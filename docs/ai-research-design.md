# AIによる複数ボード戦略調査：第1ステップ設計

状態：設計案。実装・接続・公開は未実施。2026-10-13。
基準ソース：fa51f1e40d8603950ed536d6b7bff6d65df347b3。

## 目的と今回の範囲

「Ahiボードのベット戦略を、ボードの特徴ごとに調査して」と依頼すると、AIが登録データを検索し、本アプリのsyntax照合・CSV集計・EQ計算を使って比較し、出典と計算設定付きで報告する。

ユーザーが調査するsyntaxを設定する。固定のデフォルト条件だけに限定しない。今回の成果物はデータ形式、ユーザー設定、MCP機能、検証方法の設計であり、既存EXE・MCPの挙動は変えない。

## ユーザーが設定するsyntax

既存の集計画面に「調査条件セット」を置き、独立したトップレベルタブは増やさず、条件名、適用方法、syntax、使用するかどうかを編集する。同じセットを保存・複製・JSON入出力できるようにする。既存生成画面からの条件追加も残す。AIへの自然文による登録・変更依頼も、同じ条件セットに反映する。

| 適用方法 | 保存する内容 | 解決方法 |
| --- | --- | --- |
| 全ボード共通 `literal` | 条件ID、表示名、syntax、適用ボード | ユーザーが指定した同一の文字列を適用する |
| ボード別 `per_board` | 共通の条件ID・表示名、ボード→syntaxの表 | 対象ボードの明示的な定義だけを使う |
| 生成条件 `generated`（後続実装） | ユーザーが選んだ役・ドロー・ブロッカー設定 | 既存生成エンジンでボードごとに生成し、使用syntaxを保存する |

第2ステップの最初の実装対象はliteralとper_board。generatedは後続とし、未対応の型を受け取ったら明確なエラーを返す。ボードに依存する生成済み文字列は、初期値をper_boardとする。

例：`AA`を全ボードで調べるならliteral。異なるボードでトップツーペアなど同じ役を調べるならper_board、または後続のgeneratedを使用する。名称だけから役を推測しない。literalの`ss`は常にスペード2枚であり、「そのボードのフラッシュスート2枚」へ読み替えない。

- 同名条件をIDで区別する。編集でrevisionを増やし、実行中・保存済み結果は開始時の定義に固定する。
- ユーザーのsyntaxをAIが自動で修正・追加・置換しない。新しい条件は提案として分け、採用された定義だけを調査に使う。
- 条件セット未選択なら選択を求める。デフォルト185条件や全ハンドへ自動で切り替えない。
- 全ハンドは明示的な`*`条件として登録できる。空文字は全ハンドとみなさない。
- 現行SyntaxMatcherが扱う構文だけを受理する。任意のMonker構文すべてに対応しているとは説明しない。構文検証に加えて対象ボード・入力レンジで照合する。
- per_boardの未設定は`missing_definition`、構文不正は`invalid_syntax`、合法な自分レンジで該当なしは`no_matching_hands`。0%やEQ 0へ変換しない。
- 部分適用を許すかは調査計画で指定する。初期値は未設定・不正な定義があれば開始を止める。部分実行を選んだ場合も除外一覧を残す。
- フロップカードの順序だけは正規化する。ランク・スートは変換しない。スート同型ボードをまとめる変換は初期実装に含めない。
- PLOの手札2枚＋ボード3枚、既存BDSD4/8の固定2枚組・9+の3枚以上という分類は既存エンジンの責務。ユーザーの任意syntaxの名称にその保証があるとは扱わない。

## データ登録形式

研究用カタログは、複数の「局面条件」と、その条件に属するボード別の「スポット」を持つ。1スポットは同一ボード・同一アクション直前のノードを表す。CSV内容からポジションやベットサイズを推測しない。

| 対象 | 主な項目 |
| --- | --- |
| 局面条件 scenario | PLO4、HU/人数、ポジション、実効スタック、ポット種別、ストリート、アクション履歴、レーキ・ソルバー設定を識別するsolution_context |
| スポット spot | spot_id、scenario_id、スート付きボード、利用者側ノード識別子、action_set_complete |
| 自分のアクション | action_id、種類check/bet/fold/call/raise、表示名、サイズの単位と値、CSV参照 |
| 相手のアクション前レンジ | CSV参照の配列、weight単位、共通基準の確認 |
| CSV参照 | カタログ内source_id、ファイル名、ローカル相対パスまたはクラウドの所有者付き保存ID、SHA-256、インポート方式 |
| 条件セット | set_id、revision、条件ID・表示名・適用方法・syntax、選択状態 |

EQの基準点equity_referenceを明示し、双方の比較対象アクションが入る前のレンジを指定する。相手のベット／チェックで絞った事後レンジに置き換えない。基準点より前のアクションは局面条件として記録する。アクションCSVの合計が指定した基準点の自分レンジを表すかも登録時に確認し、時点の異なるレンジを混ぜない。異なるscenario_idは別の比較群とし、項目が同じに見えるだけで混合しない。不明なメタデータは不明として保持し、条件をそろえたカテゴリ集計から除外する。

自分側は全アクションのCSVを必要とし、初期実装は現行エンジンと同じ2〜3アクションに限定する。4アクション以上を黙って削らず、上限拡張を別工程とする。完全性はCSVだけで自動証明できないため、ユーザーが全アクションと共通weight基準を確認する。

CSV参照は既存MCPの一時dataset_idと区別する。カタログの参照から実行時に登録し直し、SHA-256で変更を検出する。再起動後に古い一時IDをそのまま使わない。サンプルの`data/`パスは架空の相対パスで、個人のCSVや絶対パスをソース管理しない。

アクションの比較キーは表示名だけでなく種類・サイズ単位・数値とする。bet 33%とbet 75%は別系列。記録のないサイズを0%とみなさない。総ベット頻度は明示的なbetを合算し、raiseとは区別する。表示色は研究全体でaction keyに固定する。

## 重みと数値の定義

スポットb、ハンドh、アクションaのCSV weightをw(b,h,a)とする。ボードに対して合法な自分のアクション前weightはH(b,h)=Σa w(b,h,a)。ファイルごとの正規化はしない。

条件Cのアクション頻度は、100 × Σ(h∈C) w(b,h,a) / Σ(h∈C) H(b,h)。条件のレンジ内比率はΣ(h∈C) H(b,h) / Σh H(b,h)。両方を返し、少数のハンドしか含まない条件を識別する。ゼロ分母はnullと理由を返す。条件は重複し得るので、条件の比率を足して全体を作らない。

相手は現行ImportRangeFilesでCSV間の同一物理ハンドweightを加算する。1ファイル内の重複は現行の最大weight方式を維持する。必要な全体一括スケーリングは比率を変えず、係数を記録する。7列CSVはweight優先、weight列がなければfrequencyを使用する。

EQは選択した自分の条件付きアクション前レンジ対相手のアクション前レンジ。同一物理カードを共有しない合法な対戦組に自分weight×相手weightを使い、既存EquityEngineで計算する。アクション頻度の分母を相手ブロッカーで変更しない。CSVのev・ev_diffをEQとして読まない。相手レンジがない場合、頻度は単独で調査できるがEQは欠損とする。EQ必須モードでは実行前に不足をエラーにする。

## ボード分類と横断集計

初期対象はフロップ。AhiはAを1枚以上含む3枚ボードと定義し、Aの枚数も独立した特徴として保存する。

- スート構成：rainbow / two_tone / monotone。
- ランク重複：unpaired / paired / trips。Aペアも識別する。
- A以外の実ランクと、T〜K・6〜9・2〜5のカード枚数。A以外が2枚とは仮定しない。
- ランク間隔などの客観的特徴を保持する。「つながりが強い」等の分類は定義を別途バージョン管理し、AIの印象だけで付けない。ストレート・ドローに基づく特徴は既存エンジンとの定義照合後に追加する。

特徴は複数軸で重複可能。分類定義を結果に保存する。初期集計はscenario内・同一condition_id・同一action keyで、登録済み有効ボードを等重み平均する。スポットが重複する同一局面・ボードは二重計上を拒否する。条件ごとに対象数・有効数・欠損理由・最小最大・ボード別データを併記する。

一部ボードだけにサイズが存在する場合、そのサイズの平均の対象数を明記する。カテゴリ比較は共通の有効対象を明示し、異なる欠損集合を同一標本と扱わない。自然発生確率やノード到達確率による加重は初期実装の対象外。CSV総weightを、そのままボードの出現頻度に使わない。

カテゴリEQは「登録ボード別EQの等重み平均」と表示し、レンジを合算して計算したEQと区別する。初期版ではカテゴリ全体の信頼区間を出さず、ボードごとのモンテカルロ95%区間を残す。ボード間の差と計算誤差を混同しない。

## 追加するMCP機能案

既存Windows15ツール版を壊さず、`research_`を付けた独立した入口を追加する。以下の名称は設計案。共通11ツール版のIDと混用しない。

| ツール | 入力の要点 | 出力の要点 |
| --- | --- | --- |
| research_save_catalog | カタログ、expected_revision | catalog_id、revision、登録時検証結果 |
| research_list_spots | catalog_id、scenario/board特徴、ページ指定 | 対象候補、CSV参照、欠損 |
| research_save_condition_set | 条件定義、expected_revision | set_id、revision、構文検証結果 |
| research_get_condition_set | set_id、revision | ユーザー定義そのもの |
| research_validate | スポット選択、条件セット版、EQ設定、欠損方針 | ボード×条件への解決結果、CSV検証、計算規模、plan_id |
| research_start | 検証済みplan_id、request_key | job_id、固定した入力のハッシュ |
| research_get_job / research_cancel_job | job_id | 進捗、完了・失敗・中止状態 |
| research_get_result | result_id、ボード/カテゴリ/条件、ページ指定 | 数値、状態、使用syntax、出典 |
| research_export | result_id、csv/json/svg/markdown | artifact_id、取得先 |

既存list_datasets/register_datasetをCSV探索・参照解決に再利用し、EQ用として実際のCSV本文を検証する。UIとMCPでConditionSet、ResearchCatalog、ResearchServiceを共有し、MCP層に別の計算式を持たない。

開始時は入力CSV、条件版、分類版、シード、試行数、エンジン版をスナップショット化。計画後の入力変更は開始時に拒否する。同じrequest_key・同じ入力は同じジョブ、異なる入力での再利用はエラー。重い計算はバックグラウンドで1スポットずつ処理し、進捗を取得できるようにする。中止した研究はcancelledとして確定済みボードを明示し、完了した研究と区別する。

既存EQエンジンは1条件の失敗を行ステータスとして返すため、研究サービスが構造化状態へ変換する。全体のcompletedと「全行有効」を混同しない。最終報告には成功・未設定・該当なし・EQ不能・実行失敗の件数を載せる。

最初の対応先はWindowsローカルMCP。プラグインはユーザー条件セットを読み、対象検索→検証→実行→比較→報告の手順を持つ。実際に接続するAIホストは未確定であり、特定ホストで動作確認済みとは扱わない。クラウド版は現在のWorkerに.NET Framework計算コードをそのまま持ち込めないため、EQ実行基盤と永続ジョブを別工程で設計する。

## 調査結果の形

1. 対象：局面条件、選択ボード数、分類基準、条件セット名と版。
2. 結論：対象データから確認できる頻度差と例外。要因の説明は仮説と区別する。
3. 表：カテゴリ×ユーザー条件×アクションの平均・対象数・範囲、条件のレンジ内比率。
4. 図：ボード別およびカテゴリ別のEQ×全アクション頻度。条件名とボード名を確認できる表示。
5. 根拠：使用CSVハッシュ、ボード別syntax、計算結果、設定、欠損・除外一覧。

取り込まれた戦略CSVの調査であり、未提供のボード戦略を新しく解くソルバーではない。登録標本の傾向を、全Ahiボードの傾向と断定しない。
